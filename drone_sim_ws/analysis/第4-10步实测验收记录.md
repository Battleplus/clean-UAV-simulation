# Steps 4-10 verification record (current worktree)

This record separates what is verified in Gazebo/PX4 from what is still a
provisional physical assumption. The 7.735 kg baseline is not overwritten by
the experiments below.

## Step 4-5: rotor model and allocation

- Input is eight normalized actuator commands in `[0, 1]`.
- The supplied static table is used at 14.8 V and capped at 11.76798 N per
  motor (1.2 kgf). There is still no RPM, `C_T`, or `C_Q` measurement.
- Each command produces a per-motor force and torque record. The allocation
  matrix is 6 x 8, rank 6, condition number about 23.3225.
- The bounded hover solution for 7.735 kg has residual norm `2.98e-14 N/Nm`
  and no saturation. An impossible `Fz=-200 N` request correctly reports
  upper saturation and a large residual.
- `Q/T=0.001 m` remains a temporary reaction-torque estimate. Propeller pitch
  signs for 4/5/7/8 remain a CAD/manufacturer confirmation item.

## Step 7: motor/ESC/battery dynamics

Implemented in `gazebo_direct_motor_model.py`:

- simulation-time transport delay (`0.008 s`);
- asymmetric first-order rise/fall response (`0.035/0.035 s`);
- measured static current interpolation;
- optional Thevenin battery model (SOC, loaded voltage, current, voltage
  exponent and output scaling);
- `MOTOR_DYNAMIC_STATE` telemetry in the Gazebo log;
- command-line/launch overrides so the baseline JSON remains battery-disabled.

Offline acceptance with an explicitly experimental 0.5 mOhm, 20 Ah battery:

```text
rise_t63=0.035 s, rise_t95=0.105 s, fall_t63=0.035 s
minimum thrust scale=0.9825, vertical margin after sag=4.224 N
MOTOR_BATTERY_DYNAMICS_PASS
```

A pure takeoff/hover/land run with battery dynamics enabled and zero internal
resistance completed without failsafe. A conservative 0.05 mOhm / 20 Ah
experimental run on 2026-08-08 also passed the closed-loop gate:

```text
loaded voltage ≈14.709 V, minimum thrust scale ≈0.9878
max settled horizontal error = 0.087 m
max settled height error = 0.268 m
motor saturation fraction = 2.68%
max sampled position step = 0.528 m
DDS_DYNAMIC_HOVER_PASS
```

A later 0.5 mOhm hover-only rerun on
2026-08-08 correctly showed about `14.6 V` loaded voltage and `0.975` thrust
scale, but failed the stability gate: maximum settled horizontal error was
`1.443 m`, recorded motor saturation was `14.8%`, and the largest sampled
position step was `1.363 m`. The earlier full-WASD 0.5 mOhm run likewise
showed `6.54 m` horizontal error and `9.6%` saturation. Therefore nonzero
battery resistance is not accepted for flight yet; the baseline remains
battery-disabled pending real pack data and controller/vehicle thrust-margin
retuning.

## Step 8: arm ground verification

Using the formal CAD dynamic URDF and the project controller overlay, the
following sequence reached every target without an out-of-limit command:

```text
retracted -> work_a -> work_b -> flight_work_a -> flight_work_b -> retracted
```

The recorded maximum tracking error was about `0.080 rad` with the current
ground-test tolerance. The startup script now requires the retracted pose to
settle to `0.08 rad` before PX4 flight is allowed to start.

The first direct ground invocation failed only because the external
`ros2_controllers` overlay was omitted; the formal startup path includes it.

## Step 9: low-amplitude arm flight

The original `flight_work_a/b` profile was intentionally tested and failed the
stability gate (large position drift), so it is not a default flight action.
The safe profile now has an automatic abort path: if drift exceeds 2 m or the
vertical deviation exceeds 1.8 m, it commands `retracted` and sends PX4 LAND.

New micro presets are 25% of the already reduced flight profile:

```text
flight_micro_a = [0.02, -0.03, 0.04, -0.025, 0.015, 0.04]
flight_micro_b = [-0.02, -0.015, 0.025, 0.01, -0.015, 0.015]
```

The micro profile completed both actions, automatic retraction and landing:

```text
ARM_FLIGHT_METRICS horizontal_drift_m=0.357 altitude_span_m=1.450
DDS_ARM_FLIGHT_PASS
```

No failsafe was observed. This is a first low-amplitude acceptance result,
not evidence that full arm work motions are safe in flight.

## Step 10: explicit coupled-dynamics layer (partially accepted)

The Gazebo multibody tree retains the formal link masses, COMs, inertias,
joint damping/friction and physical joint reactions. The new auditable layer
adds:

- real-time composite mass, COM and inertia evaluation from joint states;
- fixed-base reaction-force/torque estimation including joint damping and
  Coulomb friction;
- optional rigid end-effector payload mass/inertia;
- free-body velocity jump from an end-effector contact impulse;
- a bounded NED acceleration feed-forward topic (default limit `0.6 m/s^2`),
  disabled at the PX4 consumer unless `ARM_FEEDFORWARD_ENABLED=true`;
- runtime `ARM_COUPLING_STATE` telemetry.

Numerical three-state comparison (`scripts/analyze_arm_coupling.py`) produced:

```text
expanded work_a COM shift = 0.010541 m
example moving reaction force = 0.070510 N
example moving reaction torque = 0.156464 N m
0.25 kg payload total mass = 7.985 kg
ARM_COUPLING_ANALYSIS_PASS
```

The ROS 2 runtime node was also observed in the formal Gazebo launch and
published both reaction-wrench and feed-forward topics while a ground
`work_a -> retracted` motion ran. This proves the real-time computation path,
but it does not yet prove that feed-forward improves flight or that real
gripper collision/contact is calibrated. Servo torque-speed data, contact
geometry/impact validation and a with/without-feed-forward flight A/B test
remain pending.

## Step 11 status

An offline RL interface is now available at
`src/drone_arm_sim/drone_arm_sim/rl_env.py`. It shares the formal 7.735 kg
allocation, static thrust curve, battery model and arm mass properties. The
14-dimensional action is eight normalized motor commands plus six joint-speed
commands; the observation has 25 elements. Arm reaction force and torque are
converted from ROS FLU to PX4 FRD in the small-step curriculum model.

Validation completed:

```text
27 pytest regression tests passed
RL_ENV_SMOKE_PASS (hover, 200 steps, no termination)
RL_ENV_SMOKE_PASS (arm_pose, 200 steps, no termination)
```

This is an offline training interface, not PX4/Gazebo-in-the-loop. The Step 10
feed-forward A/B comparison, servo torque-speed calibration and real gripper
contact validation remain open gates before claiming full coupled flight or RL
completion.
